# GEO / AI Search Readiness — airlineslocations.com

Audited: 2026-08-26 · Pre-launch directory site (Astro SSR + WordPress headless CMS)

Pre-launch state: the site is fully blocked from every AI crawler and search
engine, and the content that exists behind that block is placeholder
(Lorem Ipsum) rather than real, citable facts. The score reflects that
almost nothing here is currently extractable or indexable — it is not a
critique of long-term potential, which depends entirely on lifting the

## 1. AI Crawler Access Status — CRITICAL (top finding, cross-cutting with rest of audit)

`https://airlineslocations.com/robots.txt` currently returns:
```
User-agent: *
Disallow: /
```
This is a blanket, non-crawler-specific rule generated by
`src/pages/robots.txt.ts`, gated on `isStaging` (`src/lib/config.ts`,
`STAGING` env var, defaults to `true`). It blocks **every** AI crawler
indiscriminately — there are no per-bot allow/disallow rules today (no
GPTBot, OAI-SearchBot, ClaudeBot, PerplexityBot, Google-Extended, CCBot,
anthropic-ai, or cohere-ai directives at all, just the one wildcard block).

| Crawler | Status |
|---|---|
| GPTBot | Blocked (wildcard) |
| OAI-SearchBot | Blocked (wildcard) |
| ClaudeBot | Blocked (wildcard) |
| PerplexityBot | Blocked (wildcard) |
| Googlebot / Google-Extended | Blocked (wildcard) |
| Bingbot | Blocked (wildcard) |

Additionally, every page ships `<meta name="robots" content="noindex, nofollow">`
(`BaseLayout.astro:62`, same `isStaging` flag) — a second, belt-and-suspenders
block independent of robots.txt. Both are driven by one env var and the code
comments confirm this is a deliberate pre-launch gate, not a bug:
`STAGING=true` → blocked by default; flip to `false` post-launch, no rebuild
needed.

**This is correctly flagged elsewhere in the audit as the single highest-priority
Critical item.** Noted here for completeness only — no further action needed
from the GEO analysis beyond confirming what it blocks (all of the above) and
that the site-ready code path (`isStaging=false`) already produces a clean
`Allow: /` + sitemap reference with no AI-specific carve-outs, which is fine
as a baseline (see recommendation below on crawler-specific rules).

## 3. Citability Assessment (template-level, once real data lands)

Verified against the live page
`https://airlineslocations.com/qatar-airways/qatar-airways-paris-office-in-france`
(fetched directly with authorization, bypassing the pre-launch robots block)
and confirmed structurally identical for other published office pages via
the sitemap (Turkish Airlines Miami/Leipzig/Nouakchott/Nuremberg).

**Current state — not citation-ready regardless of crawler access:**
- Body content (`ChildPageLayout.astro`, `<div class="prose" set:html={page.content} />`)
  is raw Lorem Ipsum piped straight from WordPress with **no fallback or
  validation** — nothing stops a placeholder page from publishing and being
  indexed once staging is lifted.
- Headings are non-semantic Lorem Ipsum artifacts ("The standard Lorem Ipsum
  passage, used since 1966", "Section 1.10.32 of 'de Finibus Bonorum et
  Malorum'...") — not question-based, not answer-bearing.
- The phone number is a literal placeholder string, `+1-XXX-XXX-XXXX`,
  sourced from `src/lib/config.ts` (`supportPhone`, `href: "#"`) and
  rendered in the "Call Now" card on **every** child page — this is a
  sitewide constant, not per-office data, so even once real address/hours
  are added per page, the phone number will still read as one generic
  (and currently fake) support line unless this is changed to per-office
  data.
- No address, hours, or map are present anywhere on the page — no plain text,
  no meta, no structured markup.
- No self-contained "what is the [Airline] office in [City]" answer block
  exists in the template or the content.
- og:description / twitter:description are auto-derived from the Lorem
  Ipsum body (Yoast excerpt), so even the SERP/AI snippet preview is
  currently garbage.

**Template gap (independent of content):** the layout has no dedicated,
labeled NAP (Name/Address/Phone/Hours) block — no `dl/dt/dd`, no schema-marked
fields, nothing separating "answer" from "prose." Once real content is
entered, if it's entered as free-form WYSIWYG prose in WordPress (the same
`page.content` HTML blob), it will *still* not be reliably extractable by
AI answer engines, because there's no structural guarantee the first
40–60 words state the address/phone directly, no forced passage-length
discipline (134–167 words), and no separation between the answer and
supporting narrative.

## 4. Structured Data (Schema.org / JSON-LD)

Present via Yoast SEO on the WordPress CMS side, rewritten to the site's own
origin at render time (`BaseLayout.astro`). Confirmed on the sampled office
page:
- `WebPage`, `BreadcrumbList` (x2 — one Yoast-generated, one duplicated by
  the Astro `Breadcrumbs` component itself), `WebSite`, `SearchAction`.
- **No `LocalBusiness`, `Organization`, `Place`, `FAQPage`, or `ContactPoint`
  node exists for the office pages** — this is the highest-leverage
  structured-data gap for a location directory, since it's exactly the type
  AI answer engines and Google's local/AI Overview surfaces key off.
- `datePublished` / `dateModified` are present and correctly wired
  (2026-08-25 on the sampled page) — good foundation for freshness once
  content is real.

## 5. Technical Accessibility

- Rendering is **server-side** (Astro, `prerender = false`, Node runtime on
  Hostinger) — confirmed via direct fetch: `raw_content` and rendered
  `content` are effectively identical, `is_spa: false`. This is a strong
  positive: no CSR/JS-rendering barrier for any crawler once access is
  opened.
- `Cache-Control: no-store` on every page — deliberate (per code comments)
  to avoid a CDN serving a stale staging/live robots.txt or noindex state
  after a flag flip. No negative GEO impact; just note that once live, a
  more cacheable strategy could help crawler-fetch reliability but is not
  urgent.
- No AI-crawler-specific rate limiting or blocks observed beyond the
  blanket disallow.

## Top 5 Highest-Impact Changes

1. **Flip `STAGING=false` only after real content is ready** (Critical,
   effort: trivial — env var flip, no rebuild). Do not lift the block while
   pages still contain Lorem Ipsum and placeholder phone numbers; doing so
   would let AI crawlers and Google index fake data under real airline
   names, which is worse than staying blocked. This is already correctly
   flagged as the top Critical item elsewhere in the audit — sequence it
   *after* item 2 below, not before.

2. **Replace Lorem Ipsum with real, structured office data per page**
   (Critical, effort: high — content ops, not code). Minimum viable fields
   per office: full street address, phone (real, per-office — not the
   sitewide placeholder), hours, and a one-sentence direct answer
   ("The Qatar Airways Paris office is located at [address], and can be
   reached at [phone].") as the first sentence of the page.

3. **Add a labeled NAP block to `ChildPageLayout.astro`** using semantic
   markup (`dl/dt/dd` or clearly labeled divs) separate from the free-form
   `prose` content, and make the "Call Now" phone number per-office instead
   of the single sitewide `supportPhone` constant in `src/lib/config.ts`
   (effort: medium — template + data model change, WP field addition).

4. **Add `LocalBusiness`/`Organization`/`ContactPoint` JSON-LD per office
   page**, populated from the same structured address/phone/hours fields
   once they exist (effort: medium — extend the Astro layout, doesn't
   require touching the Yoast-sourced graph). This is the single highest-
   leverage structured-data addition for a location directory.

5. **Add `llms.txt`** at `src/pages/llms.txt.ts` (mirroring the existing
   `robots.txt.ts` / `sitemap.xml.ts` pattern, same `isStaging` gate)
   summarizing site purpose and linking key sections once real content
   exists (effort: low). Optional relative to items 1–4, but cheap and
   directly on-brief for GEO.
